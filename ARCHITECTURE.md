## Назначение

Epistola — современный корпоративный мессенджер, создаваемый на Flutter с использованием Firebase.

Первоначально проект ориентирован на использование внутри предприятия, однако архитектура изначально проектируется как универсальная платформа, пригодная для дальнейшего масштабирования и использования в организациях любого размера.

Основной принцип разработки — создание системы, которая не потребует полного переписывания при росте функциональности.

---

## Долгосрочная цель

Главная цель проекта — создать единую рабочую платформу предприятия.

В долгосрочной перспективе Epistola должна объединить:

- корпоративный мессенджер;
- рабочие пространства (Spaces);
- мини-приложения;
- документы;
- рабочие задачи;
- сменные графики;
- внутренние сервисы компании;
- инструменты взаимодействия подразделений.

Таким образом Epistola должна стать не только средством обмена сообщениями, но и основной цифровой рабочей средой организации.

## Push Notification Foundation v0.6.3

Push-уведомления разделены на клиентский и доверенный серверный слои.

```text
Новое message document
        ↓
Firestore trigger onDocumentCreated
        ↓
sendMessageNotification
        ↓
Чтение memberIds чата
        ↓
Исключение senderId
        ↓
users/{uid}/devices/{installationId}
        ↓
Firebase Cloud Messaging
        ↓
Android notification channel epistola_messages
```

### Клиентский слой

Клиент отвечает за:

- запрос разрешения на уведомления;
- создание Android notification channel;
- обработку foreground, background и terminated-состояний;
- получение FCM-токена;
- сохранение токена текущего устройства;
- обработку обновления токена;
- удаление устройства при выходе из аккаунта;
- локальное отображение foreground-уведомления.

Устройство идентифицируется локальным `installationId`. Один пользователь может иметь несколько документов устройств и получать уведомления на нескольких устройствах.

### Серверный слой

Cloud Function `sendMessageNotification`:

- использует Firestore trigger `onDocumentCreated`;
- реагирует только на создание нового сообщения;
- получает участников из `memberIds`;
- исключает отправителя;
- читает зарегистрированные устройства получателей;
- отправляет multicast FCM;
- передаёт `chatId` в поле `data`;
- использует notification channel `epistola_messages`;
- удаляет невалидные регистрационные токены;
- ограничивает длину push-preview;
- записывает результат отправки в Cloud Logging.

Обновление message document, включая будущее логическое удаление, не вызывает повторный push, поскольку серверная функция не использует trigger обновления.

### Ограничение текущей навигации

`chatId` уже передаётся внутри push payload, однако клиент пока не выполняет навигацию непосредственно в соответствующий чат. Нажатие на уведомление открывает приложение на основном экране чатов. Deep link в конкретный чат будет реализован отдельным навигационным этапом.

## Заменяемый визуальный слой сообщений

Функциональная логика сообщений не должна зависеть от их внешнего вида.

Firestore, сервисы чатов, пагинация, удаление сообщений и правила безопасности хранят и обрабатывают только состояние данных. Цвета, форма пузырей, фон чата, размер текста и анимации относятся исключительно к presentation-слою.

Целевая структура:

```text
Firestore message document
        ↓
Message domain / presentation state
        ↓
MessageItem
        ↓
MessageBubble
        ↓
Chat appearance configuration
```

### Ответственность слоёв

`MessageItem` отвечает за:

- идентичность элемента через `messageId`;
- логическое состояние сообщения;
- обработку пользовательских действий;
- анимацию появления, изменения и удаления;
- замену одного визуального эффекта другим без изменения Firestore-логики.

`MessageBubble` отвечает только за отображение видимого сообщения:

- текст;
- имя отправителя;
- время;
- выравнивание;
- текущую форму и отступы;
- применение настроек оформления.

`MessagesList` отвечает за:

- загрузку страниц;
- realtime-обновления;
- Firestore-курсоры;
- сортировку документов;
- сохранение позиции прокрутки;
- передачу подготовленных данных в визуальный слой.

### Будущая настройка внешнего вида

Архитектура должна позволять централизованно менять:

- светлую и тёмную темы;
- пользовательские цветовые темы;
- фон или обои чата;
- форму входящих и исходящих пузырей;
- максимальную ширину пузырей;
- внутренние и внешние отступы;
- размер, насыщенность и стиль текста;
- отображение имени и времени;
- расстояние между сообщениями;
- анимации появления и удаления;
- компактный и расширенный режимы интерфейса.

Для этих параметров в дальнейшем должен использоваться единый объект конфигурации оформления, например `EpistolaChatTheme`, подключаемый через Flutter theme layer или `ThemeExtension`.

Жёстко заданные визуальные значения не должны распространяться по сервисам, моделям и Firestore-коду.

### Удаление сообщений

В `v0.6.4` реализовано логическое удаление сообщений без физического удаления Firestore-документов.

Поддерживаются два сценария:

- **Удалить у себя** — сообщение скрывается только для текущего пользователя.
- **Удалить у всех** — собственное сообщение отправителя становится недоступным всем участникам чата.

Физическое удаление документов не используется, поскольку оно могло бы нарушить:

- cursor pagination;
- стабильность загруженных страниц истории;
- связь через `lastMessageId`;
- восстановление предыдущего превью;
- предсказуемость Firestore listener;
- аудит и последующую модерацию.

#### Состояния представления сообщения

Клиент преобразует Firestore-документ в модель `MessagePresentation`.

```text
Firestore document
        ↓
MessagePresentation
        ↓
MessageItem
        ↓
MessageBubble
```

Модель поддерживает состояния:

```text
visible
hiddenForCurrentUser
deletedForEveryone
```

`MessagePresentation` содержит данные, необходимые визуальному слою:

- `id`;
- `text`;
- `senderId`;
- `senderName`;
- `createdAt`;
- `visibility`.

`MessageItem` отвечает за визуальное появление и исчезновение сообщения. Бизнес-логика удаления и Firestore-записи в нём отсутствуют.

Это позволяет позднее заменить анимации, форму пузырей и оформление сообщений без изменения сервисного слоя.

#### Удаление у себя

При удалении сообщения у текущего пользователя документ сообщения сохраняется, а в поле персонального скрытия записывается UID пользователя.

Концептуальная структура:

```text
hiddenFor: {
  userUid: Timestamp
}
```

Сообщение считается скрытым только тогда, когда UID текущего пользователя присутствует в `hiddenFor`.

Другие участники продолжают видеть исходный текст сообщения.

Операция доступна участникам чата только в отношении собственного представления истории и не изменяет содержимое сообщения для остальных пользователей.

#### Удаление у всех

Удалить сообщение у всех может только его отправитель.

После подтверждения документ обновляется логически:

```text
text: ""
deletedForEveryone: true
deletedBy: senderUid
deletedAt: server timestamp
```

Исходный документ остаётся в коллекции `messages`, но перестаёт отображаться у всех участников.

Firestore Security Rules проверяют:

- пользователь авторизован;
- пользователь является участником чата;
- пользователь является отправителем сообщения;
- сообщение ещё не было удалено у всех;
- изменяются только разрешённые поля;
- `text` очищается;
- `deletedForEveryone` получает значение `true`;
- `deletedBy` совпадает с UID отправителя;
- `deletedAt` записывается серверным временем.

Физическая операция `delete` для документов сообщений запрещена правилами.

#### Метаданные последнего сообщения

Карточка чата хранит связь с последним сообщением через:

```text
lastMessage
lastMessageId
lastMessageAt
```

Для логического удаления используются дополнительные поля:

```text
lastMessageHiddenFor
lastMessageDeletedForEveryoneId
```

`lastMessageHiddenFor` хранит персональное состояние последнего сообщения:

```text
lastMessageHiddenFor: {
  userUid: messageId
}
```

`lastMessageDeletedForEveryoneId` указывает, что текущий `lastMessageId` был удалён у всех.

При удалении сообщения, которое не является последним, метаданные карточки чата не меняются.

При удалении последнего сообщения карточка не показывает удалённый текст и выполняет поиск предыдущего видимого сообщения.

#### Поиск предыдущего видимого сообщения

Метод `findLatestVisibleMessagePreview` запрашивает последние документы истории в обратном хронологическом порядке.

При выборе превью исключаются:

- сообщения с `deletedForEveryone == true`;
- сообщения, скрытые для текущего пользователя;
- сообщения, созданные до персональной очистки чата через `clearedAtByUser`.

Результат содержит:

```dart
({String text, Timestamp createdAt})?
```

Карточка чата использует найденные `text` и `createdAt` как эффективное последнее сообщение и его время.

Предыдущее превью вычисляется отдельно для каждого пользователя, поскольку персонально скрытые сообщения могут различаться.

#### Сервисный слой

Публичный `ChatService` делегирует операции специализированному сервису сообщений:

```text
ChatService
        ↓
ChatMessagesService
        ↓
Cloud Firestore
```

Основные операции:

```dart
deleteMessageForCurrentUser(...)
deleteMessageForEveryone(...)
findLatestVisibleMessagePreview(...)
```

`ChatService` остаётся фасадом для экранов и виджетов. Firestore-транзакции и структура документов сосредоточены в `ChatMessagesService`.

#### Пагинация и realtime

Логически удалённые документы сохраняются в результатах Firestore-запросов, поэтому курсоры остаются стабильными.

Клиент получает обновление документа через существующий realtime listener, преобразует новое состояние в `MessagePresentation` и запускает исчезновение через `MessageItem`.

Загруженные старые страницы истории не сбрасываются. Удалённые сообщения не возвращаются при:

- realtime-обновлении;
- прокрутке старой истории;
- повторном открытии чата;
- перезапуске приложения.

#### Push-уведомления

Cloud Function `sendMessageNotification` использует trigger создания документа сообщения.

```text
onDocumentCreated
```

Логическое удаление выполняется операцией update, поэтому:

- повторное push-уведомление не отправляется;
- удалённый текст не создаёт нового события уведомления;
- серверная push-логика не требует отдельного исключения удаления.

#### Ограничения этапа

Этап фиксирует фундамент удаления. Связанные ошибки, обнаруженные при дальнейшей эксплуатации, исправляются отдельными коммитами.

Будущее визуальное обновление сообщений может заменить:

- продолжительность исчезновения;
- кривую анимации;
- масштабирование;
- прозрачность;
- форму пузырей;
- цветовую схему;
- отображение заглушки удалённого сообщения.

Эти изменения не должны затрагивать Firestore-схему, Security Rules, пагинацию или сервисы удаления.

## Media Storage Strategy

Firebase Storage подключён, но должен использоваться экономно.

На первом этапе Firebase Storage используется для лёгких и системных медиа:

- аватары пользователей;
- аватары групп;
- изображения, связанные с профилями и карточками;
- небольшие превью.

Для тяжёлых медиа требуется отдельное архитектурное решение:

- фотографии;
- видео;
- голосовые сообщения;
- документы;
- крупные вложения.

Перед загрузкой медиа в облако необходимо предусмотреть:

- сжатие изображений;
- сжатие видео;
- сжатие голосовых сообщений;
- генерацию превью;
- ограничения по размеру файлов;
- локальное кеширование;
- очистку старых локальных файлов.

В будущем нужно рассмотреть гибридную модель хранения:

- Firebase Storage — для системных и небольших файлов;
- устройство пользователя — для локального хранения и кеша;
- внешние облака, например Google Drive или Яндекс Диск — для тяжёлых файлов и документов.

Firestore при этом должен хранить не сами файлы, а только метаданные:

- тип файла;
- размер;
- имя;
- владелец;
- chatId;
- downloadUrl или externalUrl;
- createdAt;
- storageProvider.

## Avatar Image Pipeline v0.6.5

### Общий поток

Пользовательский avatar pipeline построен как последовательность изолированных слоёв:

```text
ProfileAvatarEditor
        ↓
AvatarReplacementController
        ↓
AvatarImagePreparationService
        ↓
picker gateway/service
        ↓
crop gateway/service
        ↓
AvatarImageProcessor + compressor gateway
        ↓
PreparedAvatarImages
        ↓
AtomicAvatarReplacementService
        ↓
AvatarStorageUploadService + storage gateway
        ↓
UserAvatarMetadataGateway
        ↓
best-effort удаление предыдущей Storage-версии
```

`AvatarImagePreparationService` оркестрирует picker → crop → processor и возвращает только два принадлежащих pipeline подготовленных файла. `AtomicAvatarReplacementService` принимает этот результат, управляет Storage upload и только затем заменяет Firestore metadata.

Оригинал, полученный от `image_picker`, не передаётся в Storage. Загружаются только:

```text
JPEG thumbnail  128x128
JPEG full       512x512
```

### Назначение gateway, service и controller

Gateway-классы изолируют плагины и Firebase SDK:

- `ImagePickerAvatarImagePickerGateway` адаптирует `image_picker`, источники gallery/camera и `retrieveLostData()`;
- `ImageCropperAvatarImageCropGateway` адаптирует `image_cropper` и фиксирует квадратный crop `1:1`;
- `FlutterImageCompressAvatarImageCompressorGateway` адаптирует `flutter_image_compress`;
- `FirebaseAvatarStorageGateway` выполняет upload/delete через Firebase Storage;
- `FirebaseUserAvatarMetadataGateway` выполняет транзакционную замену metadata в `users/{uid}`;
- `FirebaseAvatarImageSource` читает байты по Storage path через аутентифицированный Firebase Storage SDK.

Service-классы содержат правила сценария:

- `AvatarImagePickerService` предоставляет gallery/camera и выбирает первый восстановленный image result;
- `AvatarImageCropService` проверяет вход и запускает квадратный crop;
- `AvatarImageProcessor` создаёт варианты, применяет политику сжатия и владеет своей временной директорией;
- `AvatarImagePreparationService` связывает picker, crop и processor и отвечает за промежуточный crop-файл;
- `AvatarStorageUploadService` проверяет жёсткие пределы, строит версионные пути, загружает оба варианта и удаляет неполную новую версию при ошибке upload;
- `AtomicAvatarReplacementService` задаёт порядок удалённых операций и всегда инициирует финальный best-effort cleanup локальных outputs; фактическое удаление не гарантируется при системных или файловых сбоях.

`AvatarReplacementController` — application/controller слой для UI. Он:

- сериализует одну ручную замену;
- возвращает состояния `success`, `cancelled`, `failure`, `alreadyRunning`;
- различает ошибки preparation и replacement;
- хранит последний успешно записанный `UserAvatar` для немедленного обновления UI;
- запускает recovered image через тот же preparation/replacement pipeline;
- ждёт завершения ручной операции перед lost data recovery.

Виджеты аватара не выполняют Firestore-запросы. `ProfilePage` получает профиль из Firestore и передаёт `AppUser` вниз; `ChatsPage` разрешает и пакетно загружает профили собеседников через chat/service слой. `UserAvatarView` и `AvatarView` работают только с готовой моделью, `AvatarImageLoader` и fallback URL.

### Crop, ориентация и сжатие

Crop ограничен прямоугольной квадратной областью `1:1`; промежуточный JPEG создаётся с максимальной стороной `1024` и quality `100`.

`AvatarImageProcessor` создаёт:

- thumbnail `128x128`, JPEG quality `75`, hard limit `128 KB`;
- full `512x512`, JPEG quality attempts `82, 76, 70, 64, 58, 52, 46, 40, 34`.

Для каждого output передаются `autoCorrectionAngle: true`, `keepExif: false` и `rotate: 0`. Таким образом ориентация исправляется компрессором, а EXIF не переносится в итоговые файлы.

Для full целевой размер равен `300 * 1024` bytes. Пока результат больше цели и остаются quality attempts, предыдущий файл удаляется и выполняется повторное сжатие. Последний результат между `300 KB` и `512 KB` допускается; результат больше `512 KB` отклоняется. Перед Storage upload размеры обоих вариантов проверяются повторно.

Отмена source sheet, системного picker или crop возвращает `cancelled` и не считается ошибкой. При ошибке подготовки UI показывает причину на уровне выбора, crop или обработки. При ошибке удалённой замены пользователь получает сообщение, что новый аватар не сохранён; прежний аватар остаётся активным.

### Ownership временных файлов и cleanup

Ownership задаётся явно:

- source path от `image_picker` принадлежит платформе/plugin и не удаляется pipeline;
- crop output принадлежит `AvatarImagePreparationService`, только если его path отличается от source path;
- временная директория `epistola_avatar_*`, thumbnail, full и отклонённые попытки принадлежат `AvatarImageProcessor`;
- `PreparedAvatarImages` передаёт вызывающему коду только право использования и идемпотентный `cleanup()`.

Crop output удаляется best-effort после processor независимо от успеха. Отклонённые full attempts удаляются перед следующей попыткой. При ошибке processor очищает созданную им директорию, не заменяя исходную ошибку ошибкой cleanup.

После подготовки `AvatarReplacementController` и `AtomicAvatarReplacementService` оба могут вызвать `PreparedAvatarImages.cleanup()`: операция идемпотентна, параллельные вызовы объединяются, а после transient failure допускается повторная попытка. Ошибка локального cleanup не должна маскировать результат удалённой операции.

### Версионные Storage paths и metadata

Новая версия получает положительный монотонный номер на основе `microsecondsSinceEpoch`:

```text
user_avatars/{uid}/v{version}/thumb.jpg
user_avatars/{uid}/v{version}/full.jpg
```

Firestore document `users/{uid}` хранит:

```text
avatarProvider
avatarThumbStoragePath
avatarFullStoragePath
avatarThumbSizeBytes
avatarFullSizeBytes
avatarVersion
avatarUpdatedAt
```

Thumbnail и full обязаны иметь одного владельца, provider и version. Download URL не является источником истины и новым pipeline не записывается.

### Атомарная замена и rollback

Порядок замены фиксирован:

```text
1. upload новой версии thumbnail и full
2. транзакционная запись новых metadata в Firestore
3. best-effort удаление thumbnail и full предыдущей версии
```

До шага 2 старые metadata остаются источником истины. Если upload одного из вариантов не удался, `AvatarStorageUploadService` best-effort удаляет оба пути неполной новой версии.

Если Firestore transaction завершилась ошибкой, `AtomicAvatarReplacementService` выполняет rollback: best-effort удаляет только что загруженную новую версию и повторно выбрасывает исходную ошибку. Старая версия остаётся активной. После успешной записи metadata ошибка удаления старых файлов не отменяет новую версию и не заменяет успешный результат.

### Version conflict protection

`FirebaseUserAvatarMetadataGateway` читает активную версию и обновляет документ в Firestore transaction. `requireNewerAvatarVersion()` отклоняет candidate, если `candidateVersion <= activeVersion`.

Та же граница продублирована в Firestore Rules: изменение avatar-controlled fields разрешено только владельцу, только полным набором metadata и только при строго возрастающем `avatarVersion`. При конфликте rollback не удаляет путь версии, которая уже стала активной: `activeVersion` передаётся в защитный delete guard.

Это защищает от позднего завершения конкурирующей операции и от перезаписи более нового аватара старым.

### Path-first загрузка и AvatarImageCache

`UserAvatarView` выбирает thumbnail или full Storage path из `AppUser.effectiveAvatar`. `AvatarView` передаёт `path`, `version` и hard byte limit в общий `AvatarImageLoader`.

Текущая реализация `AvatarImageCache`:

- читает объект через `FirebaseStorage.ref(path).getData(maxSizeBytes)`, поэтому применяются Firebase Authentication и Storage Rules;
- использует ключ `path@version`;
- хранит LRU-кэш максимум из 64 записей в памяти процесса;
- при cache hit обновляет позицию записи;
- дедуплицирует параллельные чтения одинакового `path@version` через карту `_inFlight`;
- повторно проверяет максимальный размер полученных байтов;
- удаляет failed future из `_inFlight`, поэтому следующий rebuild может повторить чтение.

Path-first кэш пока не является постоянным disk cache и очищается при завершении процесса. Legacy URL загружается через `CachedNetworkImage`, у которого остаётся собственное memory/disk caching.

Если path-first metadata отсутствует или path-first чтение не дало пригодного изображения, `AvatarView` пробует совместимый URL. `AppUser` поддерживает прежние `avatarThumbUrl` / `avatarFullUrl` metadata и поле `avatarUrl`; последнее используется как конечный legacy fallback. Если URL также отсутствует или не загрузился, показывается стабильный fallback с инициалами.

### Storage и Firestore security model

Storage Rules для `user_avatars/{userId}/{version}`:

- разрешают `get` только аутентифицированным пользователям и только для версии вида `v[1-9][0-9]*`;
- не разрешают list через avatar match;
- разрешают create/update/delete только владельцу `request.auth.uid == userId`;
- принимают только `image/jpeg`;
- ограничивают thumbnail до `128 KB`, full до `512 KB`;
- не дают avatar match для произвольных имён файлов.

Firestore Rules для `users/{uid}`:

- разрешают чтение только после входа;
- разрешают create/update профиля только его владельцу, delete запрещён;
- проверяют provider `firebase`, точные owner-bound versioned paths, размеры, положительную версию и timestamp;
- разрешают avatar update только через avatar metadata keys и требуют строго возрастающую версию;
- не позволяют новым user documents записывать непустой legacy `avatarUrl` или поля `avatarThumbUrl` / `avatarFullUrl`.

Клиентские проверки нужны для понятной ошибки и раннего отказа, но не заменяют Firebase Security Rules.

### Android lost data recovery lifecycle

`HomeScreen` создаёт один `AvatarReplacementController` для пользовательской сессии и оборачивает основной UI в `AvatarLostDataRecoveryHost`.

Host планирует recovery после первого frame в `initState`; при замене `uid`, controller или coordinator повторно планирует вызов, но `AvatarLostDataRecoveryCoordinator` разрешает только одну фактическую попытку за запуск приложения. Guard построен как `!kIsWeb && defaultTargetPlatform == TargetPlatform.android`, поэтому `retrieveLostData()` не вызывается на Web и не-Android платформах.

Coordinator помечает попытку до первого `await`, что защищает от параллельных lifecycle notifications. Gateway вызывает `image_picker.retrieveLostData()`, принимает только image result и передаёт первый файл в обычные crop, processor, upload и atomic replacement. Пустой result трактуется как cancel/no-op. Ошибка recovery показывает SnackBar и сохраняет старый аватар.

### Текущее отображение и ограничения

Реализовано:

- full-вариант в профиле;
- thumbnail собеседника в списке личных чатов;
- path-first изображение, legacy URL и fallback с инициалами;
- локальное немедленное отображение новой версии до прихода Firestore stream.

Не завершено:

- в заголовке уже открытого личного чата `ChatAppBarTitle` пока использует старый однобуквенный `CircleAvatar`, а не `UserAvatarView`;
- это следующий отдельный шаг;
- групповые чаты в этом шаге менять нельзя;
- path-first cache пока только in-memory;
- отображение аватаров в поиске, контактах и карточках участников не входит в текущую реализацию.

Оставшиеся проверки на физическом Android-устройстве:

- gallery и camera, включая permission denial и отмену;
- crop `1:1`, отмену crop и реальные большие изображения;
- правильную ориентацию фото с EXIF rotation и отсутствие EXIF в outputs;
- фактические размеры thumbnail/full и повторные quality attempts;
- upload/read с развёрнутыми Storage и Firestore Rules под разными пользователями;
- атомарную замену при сетевой ошибке и сохранение старого аватара;
- lost data recovery после уничтожения Activity/процесса Android;
- обновление профиля и списка личных чатов после смены версии;
- fallback при недоступном Storage object и при legacy `avatarUrl`.

# Архитектурные решения

Данный раздел фиксирует ключевые решения, которые считаются фундаментальными для проекта.

Эти решения не должны изменяться без серьёзной необходимости.

---

## Firebase Authentication используется только для авторизации

Firebase Authentication отвечает исключительно за вход пользователя в систему.

Он не используется как источник данных профиля.

В профиле пользователя не должны храниться данные, напрямую зависящие от Firebase Authentication.

Это позволяет в будущем безболезненно добавить:

- вход по телефону;
- Google Sign-In;
- Microsoft;
- Apple;
- другие способы авторизации.

---

## Профиль пользователя хранится отдельно

Информация профиля располагается в коллекции `users`.

Публичный контактный E-mail не зависит от E-mail авторизации.

Телефон также является обычным полем профиля.

Такое разделение делает профиль независимым от механизма входа в систему.

---

## UID является главным идентификатором

Во всём проекте основным идентификатором пользователя считается только Firebase UID.

E-mail используется исключительно как дополнительная информация.

Никакая критическая логика не должна строиться только на адресах электронной почты.

---

## Firestore — источник истины

Главное состояние приложения всегда хранится в Firestore.

Интерфейс отображает данные Firestore, но не является источником истины.

Это обеспечивает:

- синхронизацию нескольких устройств;
- корректную работу нескольких пользователей;
- возможность дальнейшего масштабирования.

---

## Firestore Rules являются частью архитектуры

Правила безопасности Firestore рассматриваются как полноценная часть серверной логики.

Проверки, влияющие на безопасность приложения, не должны выполняться только пользовательским интерфейсом.

Даже модифицированный клиент не должен иметь возможности обойти ограничения ролей или модерации.

---

## ChatService является фасадом

Пользовательский интерфейс взаимодействует только с `ChatService`.

Внутреннее устройство сервисов может изменяться без изменения экранов приложения.

Такой подход обеспечивает стабильный публичный API и упрощает дальнейший рефакторинг.

---

## Большие сервисы разделяются

При увеличении размера сервисов они разделяются на специализированные компоненты.

На текущем этапе реализованы:

- ChatMessagesService
- ChatGroupsService
- ChatMembersService
- ChatPermissionsService
- ChatPrivateService
- ChatSearchService

В дальнейшем аналогичный подход будет использоваться и для других крупных подсистем.

---

## Один файл — одна ответственность

Каждый файл проекта должен иметь понятную область ответственности.

Если файл начинает содержать несколько независимых направлений логики, он должен быть разделён.

Монолитные файлы допускаются только на ранних этапах разработки.

---

## UI не содержит бизнес-логики

Экран отвечает только за:

- отображение данных;
- обработку пользовательских действий;
- вызов соответствующего сервиса.

Работа с Firebase, ролями, модерацией, поиском и сообщениями выполняется исключительно сервисами.

---

## Новые функции должны расширять архитектуру

Каждый новый этап разработки должен усиливать существующую архитектуру, а не нарушать её.

Приоритет всегда отдаётся расширению уже существующих механизмов, а не созданию альтернативных решений.

Epistola построена по принципу многоуровневой архитектуры.

На текущем этапе используется следующая схема.

# Сервисная архитектура

## Общая концепция

Практически вся бизнес-логика Epistola находится в сервисах.

Экран не должен напрямую обращаться к Firebase, если соответствующая логика уже существует в сервисном слое.

Это позволяет:

- уменьшить связанность проекта;
- облегчить тестирование;
- безопасно выполнять рефакторинг;
- использовать одну и ту же бизнес-логику несколькими экранами.

---

## ChatService

ChatService является публичным фасадом системы сообщений.

Все экраны работают именно с ним.

Внутри ChatService вызовы распределяются между специализированными сервисами.

Такой подход позволяет менять внутреннюю архитектуру без изменения пользовательского интерфейса.

---

## ChatBaseService

Базовый сервис.

Предоставляет наследникам:

- FirebaseAuth;
- FirebaseFirestore;
- общие методы;
- общие проверки.

Все специализированные сервисы наследуются именно от него.

---

## ChatMessagesService

Отвечает исключительно за сообщения.

Основные обязанности:

- получение списка сообщений;
- отправка сообщений;
- отметка сообщений как прочитанных;
- подсчёт непрочитанных сообщений;
- обновление последнего сообщения чата;
- автоматическое снятие временных ограничений после окончания срока действия.

В будущем сюда будет перенесена работа со всеми типами вложений.

---

## ChatGroupsService

Отвечает за жизненный цикл групп.

Основные функции:

- создание группы;
- изменение названия;
- выход участников;
- безопасный выход администратора;
- передача прав;
- роспуск группы;
- управление составом группы.

---

## ChatMembersService

Работает исключительно с участниками.

Основные функции:

- получение участников;
- поиск пользователей;
- добавление участников;
- изменение ролей;
- получение информации о пользователе.

---

## ChatPermissionsService

Отвечает за права доступа.

Содержит всю бизнес-логику:

- ролей;
- mute;
- ban;
- guest;
- разрешений на отправку сообщений;
- ограничений группы.

Все изменения прав должны проходить через этот сервис.

---

## ChatPrivateService

Полностью отвечает за личные чаты.

Основные задачи:

- поиск существующего личного диалога;
- создание нового;
- восстановление старых структур данных при необходимости;
- поддержание единого алгоритма формирования private chat.

В проекте используется принцип:

> между двумя пользователями существует только один личный чат.

---

## ChatSearchService

Отвечает за поиск.

Поддерживает:

- поиск пользователей;
- поиск по имени;
- поиск по телефону;
- поиск по публичному email;
- получение списка пользователей;
- получение списка чатов.

Поиск должен быть максимально независим от экранов.

# Cloud Firestore

- работу нескольких пользователей одновременно;

# Firestore Rules

Безопасность Epistola строится не только на пользовательском интерфейсе.

Основной уровень защиты реализован именно через Firestore Rules.

Даже модифицированное клиентское приложение не должно иметь возможности:

- изменить собственную роль;
- снять собственный бан;
- писать сообщения при отсутствии прав;
- читать чужие чаты;
- получить доступ к закрытым данным.

Все критические проверки должны существовать одновременно:

- в пользовательском интерфейсе;
- в сервисном слое;
- в Firestore Rules.

---

## Роли

Поддерживаются роли:

```text
owner

admin

moderator

member

guest
```

Каждая роль определяет доступные действия пользователя внутри конкретной группы.

---

## Статусы

Поддерживаются статусы:

```text
normal

muted

banned
```

Статус является отдельной сущностью и не зависит от роли пользователя.

Например:

Администратор может временно получить статус `muted`.

---

## Message Permission

Каждая группа хранит собственные настройки отправки сообщений.

Поддерживаются режимы:

```text
all

moderators

admins
```

Настройки проверяются одновременно:

- пользовательским интерфейсом;
- сервисами;
- Firestore Rules.

# Spaces

## Общая концепция

Spaces являются стратегическим направлением развития проекта Epistola.

Несмотря на внешнее сходство с группами, **Spaces не являются чатами**.

Это отдельная архитектурная подсистема, предназначенная для организации рабочих процессов предприятия.

Главная задача Spaces — объединить общение сотрудников и рабочие инструменты внутри единой среды.

Чат является лишь одним из возможных модулей Space.

---

## Основная идея

Space представляет собой рабочее пространство.

Рабочее пространство может соответствовать:

- подразделению;
- отделу;
- смене;
- бригаде;
- проекту;
- объекту;
- филиалу;
- любой другой организационной единице.

Каждый Space обладает собственным набором доступных модулей.

---

## Spaces не являются группами

Это одно из фундаментальных архитектурных решений проекта.

Группа предназначена исключительно для общения пользователей.

Space является рабочей платформой.

Следовательно:

- группа может существовать без Space;
- Space может содержать несколько чатов;
- чат может быть только одним из модулей Space.

Данные сущности не должны объединяться.

---

## Модульная архитектура

Каждый Space состоит из независимых модулей.

Примеры модулей:

- Chat
- Shift Schedule
- Tasks
- Announcements
- Documents
- Contacts
- Calendar
- Knowledge Base
- Reports
- Forms

Архитектура должна позволять подключать новые модули без изменения существующих.

---

## Доступные модули

Каждый Space хранит перечень модулей, разрешённых администраторами.

Например:

```text
Available Modules

✓ Chat

✓ Schedule

✓ Tasks

✓ Documents

✓ Announcements

✗ Reports
```

Пользователь не может самостоятельно использовать модуль, который отсутствует в списке доступных.

---

## Персональные модули

Каждый пользователь хранит собственный список включённых модулей.

Например:

```text
Enabled Modules

✓ Chat

✓ Schedule

✓ Tasks

✗ Documents

✗ Announcements
```

Таким образом пользователь самостоятельно настраивает собственное рабочее пространство.

Отключение модуля скрывает его только для данного пользователя.

Остальные участники продолжают работать без изменений.

---

## Dashboard

В дальнейшем Space должен открываться не списком модулей, а персональной рабочей панелью.

Dashboard может содержать:

- сегодняшнюю смену;
- ближайшие задачи;
- новые документы;
- последние объявления;
- непрочитанные сообщения;
- быстрые действия.

Каждый пользователь сможет настраивать Dashboard под собственные задачи.

# Release Process

Каждый стабильный релиз проходит одинаковый цикл.

1. Завершение функциональности.
2. Тестирование.
3. Проверка `flutter analyze`.
4. Сборка Release APK.
5. Проверка на устройстве.
6. Обновление README.md.
7. Обновление ARCHITECTURE.md.
8. Commit.
9. Push.
10. Git Tag.
11. Проверка GitHub.

Нарушение данной последовательности не рекомендуется.

# Правила разработки

При дальнейшем развитии проекта должны соблюдаться следующие правила.

- Не ломать существующую архитектуру без серьёзной причины.
- Новая функциональность должна расширять существующую систему.
- Один файл — одна ответственность.
- UI не содержит бизнес-логики.
- Firestore Rules обязательны для всех критических операций.
- Firebase вызывается преимущественно через сервисы.
- Документация обновляется одновременно с кодом.
- После стабильной версии создаётся Git Tag.
- Для Firebase CLI на Windows используются команды через `firebase.cmd`.

# Неприкосновенные архитектурные решения

Следующие решения считаются фундаментальными.

Их изменение требует серьёзного архитектурного обоснования.

- Firebase Authentication используется только для авторизации.
- Профиль пользователя хранится отдельно в Firestore.
- UID является единственным основным идентификатором пользователя.
- Firestore является источником истины.
- Firestore Rules являются обязательной частью безопасности.
- ChatService остаётся фасадом сервисной архитектуры.
- Большие сервисы разделяются по зонам ответственности.
- UI не содержит бизнес-логики.
- Spaces не являются группами.
- Чат является лишь одним из модулей Space.
- Пользователь самостоятельно управляет отображением доступных модулей своего Space.
- Файлы хранятся в Firebase Storage, а не в Firestore.

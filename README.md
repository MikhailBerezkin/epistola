# Epistola

> **Современный корпоративный мессенджер на Flutter и Firebase**

Epistola — долгосрочный проект корпоративной коммуникационной платформы. Сейчас это Android-first мессенджер на Flutter и Firebase, но архитектура постепенно готовится к Web/iOS, модульным рабочим пространствам Spaces, медиа-подсистеме, возможной смене backend-хранилища и будущему собственному backend.

В ветке `feat/v0.6.5-avatar-foundation` реализован **Avatar Image Pipeline**: выбор фото из галереи или камеры, квадратный crop, создание JPEG-вариантов `128x128` и `512x512`, безопасная версионная загрузка в Storage, атомарная замена metadata в Firestore и отображение аватара в профиле и списке личных чатов.

Android-клиент восстанавливает потерянный результат `image_picker` после пересоздания Activity. Отмена выбора или crop не считается ошибкой, а при любой ошибке подготовки, загрузки или записи metadata старый аватар остаётся активным.

Известное незавершённое: в заголовке уже открытого личного чата пока используется старый однобуквенный fallback вместо `UserAvatarView`. Это следующий отдельный шаг; групповые чаты в нём менять нельзя.

Известное ограничение push-навигации сохраняется: нажатие на уведомление открывает приложение, но ещё не выполняет переход непосредственно в нужный чат.

## ⚡ Что такое Epistola

**Epistola** — корпоративный мессенджер, который создаётся как единая коммуникационная платформа для сотрудников компании.

Краткосрочная цель — стабильный мессенджер для пилотной группы примерно 40–50 пользователей.

Долгосрочная цель — рабочая платформа для компании на 600–700 сотрудников с чатами, группами, ролями, Spaces, мини-приложениями, файлами, рабочими сменами, задачами, объявлениями, документами и внутренними сервисами.

Проект развивается по принципу:

> Сначала надёжная архитектура, затем функциональность поверх неё.

### 🗑 Message Deletion Foundation

В `v0.6.4` реализован фундамент логического удаления сообщений:

- Добавлено удаление отдельного сообщения «у себя».
- Добавлено удаление собственного сообщения «у всех».
- Действие «Удалить у всех» доступно только отправителю сообщения.
- Перед удалением у всех показывается дополнительное подтверждение.
- При удалении «у себя» сообщение скрывается только для текущего пользователя через поле `hiddenFor`.
- При удалении «у всех» текст сообщения очищается, а документ получает признаки `deletedForEveryone`, `deletedBy` и `deletedAt`.
- Документы сообщений физически не удаляются из Firestore, что сохраняет стабильность курсоров и пагинации.
- Удалённые сообщения плавно исчезают из интерфейса через отдельный `MessageItem`.
- Состояние отображения отделено от Firestore-документа моделью `MessagePresentation`.
- Если удаляется последнее сообщение, карточка чата показывает предыдущее видимое сообщение.
- Предыдущее сообщение определяется отдельно для каждого пользователя с учётом персонального скрытия.
- Логическое удаление не вызывает повторный push, поскольку Cloud Function реагирует только на создание нового документа.
- Обновлены и развёрнуты Firestore Security Rules.
- Личные и групповые сценарии удаления проверены на физических Android-устройствах.

Поддерживаемые состояния сообщения:

```text
visible
hiddenForCurrentUser
deletedForEveryone
```

Удаление спроектировано как независимый слой:

```text
Firestore message state
        ↓
MessagePresentation
        ↓
MessageItem
        ↓
MessageBubble
```

Это позволяет в дальнейшем менять анимацию исчезновения, форму пузырей, цвета и другие элементы оформления без изменения Firestore-логики и сервисов чатов.

### 🖼 Avatar Image Pipeline

В `v0.6.5` реализован pipeline пользовательских аватаров:

- фото выбирается из галереи или снимается камерой;
- закрытие source sheet, отмена системного picker или crop корректно завершают операцию без изменения аватара;
- на Android поддержан `image_picker.retrieveLostData()` после пересоздания Activity;
- crop зафиксирован в квадратном соотношении `1:1`;
- из crop-результата создаются два JPEG: thumbnail `128x128` и full `512x512`;
- при сжатии включена коррекция ориентации и отключено сохранение EXIF;
- full-вариант стремится к размеру не более `300 KB`, а абсолютный предел равен `512 KB`;
- для full последовательно пробуются JPEG quality `82, 76, 70, 64, 58, 52, 46, 40, 34`;
- thumbnail имеет жёсткий предел `128 KB`;
- оригинальный файл из picker не загружается и не удаляется приложением;
- принадлежащие pipeline crop- и processing-файлы очищаются безопасно и повторяемо;
- варианты загружаются по путям `user_avatars/{uid}/v{version}/thumb.jpg` и `user_avatars/{uid}/v{version}/full.jpg`;
- замена выполняется в порядке: загрузка новой версии → транзакционная запись metadata → best-effort удаление старой версии;
- при ошибке записи Firestore новая загруженная версия удаляется как rollback, а старый аватар остаётся активным;
- ошибки показываются пользователю без потери старого аватара.

`UserAvatarView` использует path-first загрузку через аутентифицированный Firebase Storage SDK. `AvatarImageCache` хранит до 64 версионных записей в памяти и объединяет параллельные запросы одного `path@version`. Если новых path-first metadata нет или чтение Storage завершилось ошибкой, временно поддерживается legacy `avatarUrl`; при отсутствии изображения показывается стабильный fallback с инициалами.

Сейчас `UserAvatarView` используется в профиле и списке личных чатов. В заголовке уже открытого личного чата остаётся старый однобуквенный `CircleAvatar`; его замена — следующий отдельный шаг. Поведение и UI групповых чатов менять в этом шаге нельзя.

## 🧭 Архитектурная идея проекта

Epistola больше не рассматривается как просто Flutter-приложение.

Текущая архитектурная цель:

```text
Flutter client
    ↓
Domain models
    ↓
Services / Facades
    ↓
Providers / Infrastructure adapters
    ↓
Firebase сейчас
    ↓
Собственный backend / S3 / другое хранилище в будущем
```

Ключевые принципы:

- UI не должен знать детали инфраструктуры.
- Firebase используется сейчас, но не считается вечной зависимостью.
- Domain-модели не должны зависеть от Flutter, Firebase, Storage или UI.
- Внешние сервисы должны быть обёрнуты в сервисы/провайдеры.
- Новые крупные подсистемы сначала проектируются, затем реализуются.
- Код должен проходить `flutter analyze` без ошибок.

- Google Drive;
- собственный backend;
- локальный сервер компании;

## 🗂 MediaAsset

`MediaAsset` — это не сам файл, а паспорт файла.

Он описывает:

- уникальный id;
- provider;
- путь хранения;
- тип медиа;
- владельца;
- MIME type;
- размер;
- ширину и высоту;
- длительность;
- версию;
- даты создания/обновления;
- опциональный download URL.

Примерная логика:

```text
MediaAsset
 ├── id
 ├── provider
 ├── path
 ├── type
 ├── ownerType
 ├── ownerId
 ├── mimeType
 ├── sizeBytes
 ├── width / height
 ├── durationMs
 ├── version
 ├── createdAt / updatedAt
 └── downloadUrl?
```

`downloadUrl` не является главным источником истины. Основные поля — `provider` и `path`. Это нужно, чтобы в будущем можно было менять провайдера хранения.

## 🧩 MediaPaths

`MediaPaths` — единая точка описания структуры Storage.

Текущие пути:

```text
user_avatars/{userId}/v{version}/thumb.jpg
user_avatars/{userId}/v{version}/full.jpg
group_avatars/{chatId}/avatar.jpg
attachments/{chatId}/{messageId}/{fileName}
previews/{chatId}/{messageId}/{fileName}
```

`user_avatars/{userId}/avatar.jpg` временно сохраняется в API как legacy-путь Media Foundation, но новый avatar pipeline его не использует.

Зачем это нужно:

- не размазывать строки путей по всему проекту;
- упростить миграцию Storage;
- упростить изменение структуры файлов;
- избежать разных вариантов одного и того же пути;
- централизованно контролировать архитектуру хранения.

## 🧠 Стратегия хранения медиа

На текущем этапе Firebase Storage используется рационально и ограниченно.

### Сейчас в Firebase Storage планируется хранить

- пользовательские аватары;
- групповые аватары;
- небольшие системные изображения;
- будущие превью.

### В будущем нельзя бесконтрольно хранить

- тяжёлые фото без сжатия;
- видео;
- голосовые сообщения без сжатия;
- крупные документы;
- временные файлы без очистки.

### Будущая гибридная архитектура

Возможные направления:

- Firebase Storage для системных медиа и превью;
- локальный кэш на устройстве;
- Google Drive / Яндекс Диск / S3 / собственный backend для тяжёлых вложений;
- Firestore только для метаданных и ссылок;
- автоматическая очистка кэша;
- ограничения размеров файлов;
- генерация thumbnails/previews.

## 🖼 Аватары и кэширование

Текущая система аватаров работает так:

```text
Галерея / камера / Android lost data recovery
    ↓
Квадратный crop 1:1
    ↓
JPEG thumb 128x128 + full 512x512
    ↓
Загрузка новой версии в Firebase Storage
```

Download URL не является источником истины: новые записи используют Storage path и Firebase Authentication. Старое поле `avatarUrl` читается только как fallback совместимости.

## 🛡 Firestore и Storage Rules

Проект использует Firebase Security Rules как обязательный уровень защиты.

Firestore Rules отвечают за:

- доступ к пользователям;
- доступ к чатам;
- доступ к сообщениям;
- проверку членства в чатах;
- ограничения ролей;
- права на отправку сообщений;
- защиту от удаления данных;
- защиту последнего администратора.
- разрешение владельцу профиля менять только согласованный набор avatar metadata;
- проверку версионных путей, размеров и строго возрастающего `avatarVersion`;
- запрет записи новых legacy avatar URL.

Storage Rules отвечают за:

- чтение версионных пользовательских аватаров только аутентифицированными пользователями;
- создание, обновление и удаление пользовательского аватара только его владельцем;
- предел `128 KB` для thumbnail и `512 KB` для full;
- MIME type `image/jpeg`;
- проверку сегмента версии в формате `v{positiveInteger}`;
- запрет неизвестных путей;
- отдельные правила для групповых аватаров и будущих вложений.

Все правила должны храниться в корне проекта:

```text
firestore.rules
firestore.indexes.json
storage.rules
firebase.json
```

Инфраструктурные правила не должны лежать внутри `lib/`.

## 🧩 Spaces

Spaces — стратегическое направление развития Epistola.

Spaces не являются обычными группами или чатами. Это будущая платформа рабочих мини-приложений.

Планируемые модули:

- график смен;
- рабочие задачи;
- объявления;
- документы;
- журналы;
- заявки;
- рабочие панели;
- персональные и групповые дашборды.

Архитектурная идея Spaces:

- администраторы управляют доступными модулями пространства;
- пользователь сам включает или скрывает модули для себя;
- Space становится персонализированной рабочей панелью;
- модули могут развиваться независимо;
- в будущем Spaces могут стать основой корпоративной платформы, а не только частью мессенджера.

## 🎯 Принципы разработки

Проект развивается по следующим принципам:

- Архитектура важнее скорости разработки.
- Сначала проектирование — потом реализация.
- Каждый крупный модуль сначала проектируется как отдельная подсистема.
- UI не должен знать детали инфраструктуры.
- Firebase считается текущей инфраструктурой, но не вечной зависимостью.
- Domain-модели не должны зависеть от Firebase, Flutter или UI.
- Firestore хранит данные и метаданные, но не сами файлы.
- Медиафайлы должны проходить сжатие и ограничения размеров.
- Все пути Storage должны быть централизованы.
- После каждого крупного этапа обновляется документация.
- После каждой стабильной версии создаётся Git Tag.
- Код должен проходить `flutter analyze` без ошибок.
- Для Firebase CLI на Windows используются команды через `firebase.cmd`.
